# 도입 판정과 검증 계획 가이드

이 문서는 **사람이 판단하고 사람이 수행하는 것**을 정리한다.

`code-guideline.md`가 PR마다 판정되고 `preflight-guideline.md`가 실행 직전에 스크립트로 판정된다면,
이 문서의 항목은 **일회성 결정** 또는 **주기적 시험**이라 자동 판정 대상이 아니다.
LLM 게이트가 할 수 있는 것은 그 결정과 시험의 **기록이 있는지**까지다.

## 1. 도입 판정

### 1.1 오토스케일링

**다음을 모두 만족할 때만 도입한다.** 하나라도 미충족이면 도입하지 않는다.
오토스케일링은 없는 것보다 잘못 설정된 것이 나쁘다.

출처: 오토스케일링 설계 11장

점검 항목
* `OPS-1-01` 부하 시험에서 앱이 병목으로 확인되었는가
  DB가 병목이면 앱을 늘려도 효과가 없다.
* `OPS-1-02` `max_connections`가 목표 인스턴스 수를 수용하는가
* `OPS-1-03` 조건부 UPDATE가 구현되고 검증되었는가
* `OPS-1-04` 수명주기 훅이 구현되었는가
* `OPS-1-05` 인스턴스 기동 시간이 대응 가능한 수준인가
  5분이면 급격한 트래픽 증가에는 사실상 무력하다.
* `OPS-1-06` 최대 인스턴스 수 상한이 예산 안에 있는가
  오토스케일링은 비용 상한을 없앤다.

### 1.2 이중화 전환

`desired_capacity`를 1에서 2로 올리는 것이 전부이지만, 그 전에 확인할 것이 있다.
**앞의 셋은 1대일 때 검증할 수 없으므로 일시 증설로 미리 확인한다.**

출처: 장애 대응 목표와 아키텍처 결정 4.3절

점검 항목
* `OPS-1-07` RDS `max_connections`가 배포 중 45를 수용하는가
  앱 2대 20에 배치 인스턴스 10과 관리 커넥션을 더한 값이다. 앱만 세면 30으로 보여 여유를 과대평가한다.
* `OPS-1-09` 조건부 UPDATE가 모든 누적 연산에 적용되었는가
* `OPS-1-10` 배포 절차에 인스턴스 수를 하드코딩한 곳이 없는가

`OPS-1-08`과 2.4절의 분산 락 비교 실험 항목은 폐기했다. 배치를 전용 서버 한 대로 옮겨 락을 쓰지 않는다.
번호는 재사용하지 않는다. 검증 결과가 항목 번호로 기록되므로 뜻이 바뀌면 과거 기록이 거짓이 된다.

### 1.3 착수 전 확인이 필요한 값

측정하지 않으면 그 위에 세운 계산이 전부 가정에 기댄다.

출처: 장애 대응 목표와 아키텍처 결정 11.3절

점검 항목
* `OPS-1-11` RDS `max_connections`를 실측했는가
  이중화와 오토스케일링 상한의 전제다.
* `OPS-1-12` PITR 복원 RTO와 RPO를 리허설로 실측했는가
  현재 문서의 60분과 5분은 근거 없는 목표치다.
* `OPS-1-13` 서울 리전 ALB와 RDS 실제 단가를 요금 계산기로 검증했는가
  총액의 약 3분의 1이 추정치다.
* `OPS-1-14` 인스턴스 기동 실측 시간을 기록했는가
  워밍업과 쿨다운 계산의 출발점이다.

## 2. 검증 계획

설계한 안전장치가 실제로 동작하는지 확인한다. **주입하고 관찰하는 시험**이라 PR 단위가 아니다.

### 2.1 앱과 DB 장애

출처: 앱과 DB 장애 대응 구조 7장

점검 항목
* `OPS-2-01` `docker kill`로 컨테이너 급사를 주입하고 자동 재기동과 오류 구간을 측정했는가
* `OPS-2-02` `docker pause` 60초로 응답 정지를 주입했는가
  급사보다 정지가 위험하다. 프로세스는 살아 있어 TCP 연결은 수립되지만 응답이 없다.
* `OPS-2-03` RDS `reboot with failover`로 페일오버를 주입하고 정상화 시간을 측정했는가
  60초를 크게 초과하면 JVM DNS 캐시 설정을 확인한다.
* `OPS-2-04` 페일오버 중 톰캣 스레드가 고갈되지 않고 헬스 엔드포인트가 계속 응답했는가
* `OPS-2-05` **앱 재기동 없이 자동 복구되었는가**
  재기동해야만 복구된다면 DNS 캐시 설정이 적용되지 않은 것이다. 검증에서 가장 중요한 항목이다.

### 2.2 배포와 롤백

출처: 무중단 배포 롤링 11장

점검 항목
* `OPS-2-06` 정상 배포에서 혼재 구간과 구 인스턴스 종료 시 오류율이 0인가
* `OPS-2-07` 기동에 실패하는 이미지를 배포했을 때 신규만 종료되고 구 인스턴스가 서비스를 유지하는가
* `OPS-2-08` **배포 직후 인스턴스를 종료했을 때 교체된 인스턴스가 신 버전으로 올라오는가**
  SSM 장치가 동작하는지 확인하는 롤링 고유의 검증이다. 없으면 장애 복구가 버전 롤백을 일으키는 사고를 배포 몇 번 뒤에야 발견한다.
* `OPS-2-09` 이미지 pull 실패 시 스모크 테스트가 SHA 불일치를 잡아내는가
* `OPS-2-10` 롤백 시 SSM 값이 함께 되돌려지는가
* `OPS-2-11` **매 배포 후 롤백을 한 번씩 연습했는가**
  평소에 실행되지 않는 코드는 정작 필요한 순간에 처음 돌아간다.

### 2.3 알람

**발동하지 않는 알람은 없는 것과 같다.**

출처: 알람과 알림 설계 9장

점검 항목
* `OPS-2-12` Slack 연동 두 경로(Chatbot, Alertmanager)가 각각 도달하는가
* `OPS-2-13` 억제 규칙이 상위 알람 발동 시 하위 알람을 묻는가
* `OPS-2-14` 해소 통지가 Critical에만 오고 Warning에는 오지 않는가
* `OPS-2-15` Watchdog이 5분 주기로 도착하고 Alertmanager 중지 시 끊기는가
* `OPS-2-16` **정합성 검증 실패 알람을 테스트 데이터로 발동시켜 확인했는가**
  이 알람은 실제 사고 전까지 한 번도 발동하지 않으므로 동작 확인 기회가 없다.
* `OPS-2-17` 알람 메시지에 오차 건수, 최대 오차, 최근 변경 시각과 주체가 포함되는가
* `OPS-2-18` 설정을 Git으로 변경 후 reload로 반영되고 인스턴스 재생성 후에도 유지되는가


## 3. LLM 게이트가 할 수 있는 것

이 문서의 항목은 자동 판정 대상이 아니다. 다만 **기록의 존재는 확인할 수 있다.**

| 판정 | 가능 여부 |
|------|-----------|
| "복원 리허설을 수행했는가" | 불가 |
| "복원 리허설 기록 파일이 있고 기한 내인가" | **가능** |
| "그 기록이 성실한가" | 불가 |

따라서 이 문서의 항목은 G-AUDIT이 주기별로 **기록 누락**만 검출한다.
주기는 `lunch-catch/.github`의 `qa-llm-verification.md` 2.5절을 따른다.
