# 인프라 변경 플로우

| 항목 | 내용 |
|---|---|
| 목적 | 인프라 변경이 이슈에서 시작해 병합과 적용까지 가는 경로와, 그 길의 게이트를 한곳에 둔다 |
| 범위 | 브랜치, 보호 설정, 게이트, 리뷰(CodeRabbit 부르기와 답글), 작업 순서, 병합 뒤 적용, 위키 동기화 |
| 관련 문서 | `../../CLAUDE.md`(이슈와 PR 규칙), `../verification/verification-guideline.md`(검증 실행), `../infra-review/INFRAREVIEW.md`(리뷰 기준), `../deploy/README.md`(적용 절차) |

## 1. 브랜치

| 브랜치 | 역할 | 받는 출처 |
|---|---|---|
| `main` | 기본 브랜치. 환경이 읽는 유일한 기준 | 작업 브랜치의 PR 만 |
| `<종류>/<이슈번호>-<설명>` | 작업 브랜치 | `main` 에서 분기 |

종류는 `feat`, `fix`, `perf`, `refactor`, `chore`, `docs`, `test` 를 쓴다. 예: `fix/76-lt-free-plan`, `docs/135-workflow`.

### develop 을 두지 않는 이유

lc-backend 는 `develop` 이 개발 서버와 GHCR 이미지에, `main` 이 운영에 붙어 있어 브랜치가 곧 환경이다. `develop` 에서 먼저 돌려 보는 단계가 실제 검증이 된다.

lc-infra 는 환경이 모두 `main` 을 본다.

| 쓰는 곳 | 근거 |
|---|---|
| 모니터링 서버의 관측 설정 | 부팅 때 기본 브랜치를 받는다(`modules/compute/templates/monitoring-user-data.sh.tftpl`) |
| 개발 서버의 설정 갱신 | `origin/main` 을 받는다(`dev/templates/refresh.sh.tftpl`) |
| 부하 시험 환경 `up` | 작업 사본이 `origin/main` 과 다르면 멈춘다(`scripts/member-env.sh`) |
| 위키 동기화, CodeRabbit 의 근거 링크 | `main` 기준 |

`develop` 을 두면 거기 들어간 변경을 시험할 환경이 없어 PR 만 두 번이 된다. 인프라 변경의 실제 검증은 부하 시험 환경에 띄워 보는 것이고, 그것은 작업 브랜치에서 바로 한다(`MEMBER_ALLOW_STALE=1`, 5절).

## 2. 보호 설정

`main` 에만 건다(lc-infra #129, #133). 브랜치 보호는 저장소 설정이라 어느 파일에도 없다.

| 항목 | 값 |
|---|---|
| PR 필수 | 켬. 바로 푸시할 수 없다 |
| 필수 상태 검사 | `인프라 코드 게이트`, `레지스트리 게이트`, `이슈 게이트` |
| 최신 상태 요구(`strict`) | 끔 |
| 승인 | 1명 |
| 관리자 우회(`enforce_admins`) | 끔. 관리자는 승인 없이 병합할 수 있다(`gh pr merge --admin`). 인프라를 주로 한 사람이 다루기 때문이다 |
| 강제 푸시와 삭제 | 금지 |

## 3. 게이트

병합을 막는 것은 결정론적 검사 셋이다. 셋 다 모든 PR 에서 돈다.

| 필수 검사 | 워크플로 | 판정 |
|---|---|---|
| `인프라 코드 게이트` | `.github/workflows/terraform.yml` | Terraform 파일(`.tf`, `.tftpl`, 잠금 파일)을 바꿨으면 `envs/prod`, `envs/lt` 의 `fmt` 와 `validate` 가 통과해야 한다. 안 바꿨으면 검사를 건너뛰고 바로 통과한다 |
| `레지스트리 게이트` | `.github/workflows/registry-check.yml` | `docs/infra-review/*-guideline.md` 와 `.github/llm-verify/items.yml` 이 일치해야 한다 |
| `이슈 게이트` | `.github/workflows/pr-gate.yml` | PR 본문에 `Closes #N` 이나 `Refs #N`(다른 저장소면 `owner/repo#N`)이 있어야 한다. 본문을 고치면 다시 돈다 |

**경로 필터를 두지 않는다.** 필수 검사에 경로 필터가 걸리면 대상 파일을 안 바꾼 PR 은 검사 결과가 영영 오지 않아 병합하지 못한다. 그래서 늘 돌고, 할 일이 없으면 게이트가 바로 통과한다. `terraform.yml` 의 행렬 잡은 건너뛰면 이름이 펼쳐지지 않아 필수 검사로 걸 수 없어, 끝에 게이트 잡을 따로 둔다.

`terraform plan` 은 AWS 자격증명이 있을 때만 돈다. 없으면 건너뛰고 `fmt` 와 `validate` 만으로 판정한다.

## 4. 리뷰

LLM 리뷰는 CodeRabbit 이 맡고 **병합을 막지 않는다.** 재현율을 재지 않은 판정으로 막으면 오탐이 쌓여 우회 문화가 생긴다. 기준과 설정은 `../infra-review/INFRAREVIEW.md` 의 "PR 리뷰" 에 있다.

**자동으로 돌지 않는다.** 저장소가 공개이고 별이 10개 미만이라 CodeRabbit 이 자동 리뷰를 건너뛴다("This repository does not receive automatic reviews because it has fewer than 10 stars"). 부르지 않으면 리뷰 없이 병합된다. 그래서 아래처럼 부르고 답한다. lc-backend 도 같은 순서를 쓴다(lunch-catch/lc-backend#1191).

| 순서 | 하는 일 |
|---|---|
| 1 | PR 을 올리자마자 PR 의 `CodeRabbit` 검사가 `SKIPPED` 면 `@coderabbitai review` 를 댓글로 단다. 자동 리뷰가 돌았으면 부르지 않는다 |
| 2 | 세 게이트가 통과하는 것을 본다. 그것이 병합의 최종 판정이다 |
| 3 | 리뷰를 검토하고 **지적마다 답글을 단다.** 지적이 맞으면 고치고 고친 커밋을 답글에 적는다. 고치지 않으면 그 이유를 적는다. 인라인 지적은 그 스레드에, 본문(정리, Nitpick)의 지적은 PR 댓글로 단다 |
| 4 | 고쳐서 커밋을 올렸으면 게이트를 다시 보고, 필요하면 리뷰를 다시 부른다 |

- **부른 뒤 커밋을 올렸으면 다시 부른다.** 리뷰 도중에 커밋이 올라오면 `Head commit changed` 로 취소된다.
- **`full review` 는 쓰지 않는다.** 이미 본 커밋까지 다시 보아 시간당 리뷰 횟수를 쓴다.
- 답글이 없으면 리뷰어가 PR 만 보고 어느 지적을 고쳤고 어느 것을 왜 넘겼는지 알 수 없다.

CodeRabbit 의 첫 댓글에 있는 "Trigger review" 를 눌러도 부를 수 있다.

## 5. 작업 순서

| 순서 | 하는 일 | 규칙 |
|---|---|---|
| 1 | 이슈를 등록한다 | 일은 이슈에서 시작한다(CLAUDE.md) |
| 2 | `main` 에서 `<종류>/<이슈번호>-<설명>` 브랜치를 딴다 | |
| 3 | 고치고 커밋한다 | 커밋 제목 끝에 `(#이슈번호)`. 작성자는 로컬 git 설정 그대로(CLAUDE.md) |
| 4 | 실제 환경으로 확인할 일이면 부하 시험 환경에서 작업 브랜치로 띄워 본다 | `MEMBER_ALLOW_STALE=1 ./scripts/member-env.sh up`. 끝나면 `down` |
| 5 | PR 을 올린다 | 본문에 `Closes #N`(끝나면 닫을 이슈) 또는 `Refs #N`(확인이 남아 열어 둘 이슈). 생성 도구 언급을 넣지 않는다 |
| 6 | CodeRabbit 을 부르고 게이트를 본 뒤, 지적마다 답글을 단다 | 4절의 1 ~ 4 |
| 7 | 승인을 받아 병합한다. 혼자 다룬 변경이면 관리자가 `--admin` 으로 병합한다 | 머지 커밋으로 병합한다. 세 게이트가 통과해야 한다(3절) |
| 8 | 작업 브랜치를 지운다 | `main` 에 병합된 것을 확인하고 이름을 하나씩 지정해 지운다. 여러 브랜치를 한꺼번에 지우지 않는다 |
| 9 | 필요하면 환경에 적용한다 | 6절 |

`Closes` 는 기본 브랜치(`main`)로 가는 PR 에서 병합 시점에 이슈를 닫는다. lc-infra 는 모든 PR 이 `main` 으로 가므로 늘 걸린다.

## 6. 병합 뒤 적용

**병합이 곧 적용이 아니다.** Terraform 은 실행한 사람의 작업 사본으로 적용된다. 병합한 뒤 `main` 을 받아 손으로 돌린다.

| 대상 | 적용 | 자세한 절차 |
|---|---|---|
| 운영 | `./scripts/apply.sh`. plan 을 보고 확인한 뒤 apply 한다 | `../deploy/README.md` |
| 개발 서버 | `./scripts/dev-up.sh`. 설정 갱신은 서버의 refresh 가 `main` 을 받는다 | `../system-design/런치캐치_개발서버.md` |
| 부하 시험 환경 | `./scripts/member-env.sh up` | `../wiki/팀원-부하시험-환경.md` |
| 모니터링 서버의 관측 설정 | 서버에서 `git pull` 하고 reload 한다. 경보 규칙은 Prometheus 를 재시작해야 바뀐다 | `../../observability/README.md` |

plan 과 apply 를 확인 없이 잇지 않는다. 리소스를 만들고 지우는 일은 돈이 드는 일이라 매번 확인을 받는다.

## 7. 위키 동기화

`main` 에 `docs/wiki/**` 가 바뀌면 `.github/workflows/wiki-sync.yml` 이 GitHub 위키로 민다.

**지금은 동기화되지 않는다.** 저장소 Secrets 에 `WIKI_TOKEN` 이 없어 워크플로가 경고만 남기고 건너뛴다. 실행은 "성공" 으로 보이므로 로그의 경고를 봐야 안다. 위키를 쓰려면 위키 쓰기 권한이 있는 PAT 을 `WIKI_TOKEN` 으로 넣고, Wiki 를 켠 뒤 첫 페이지를 한 번 만든다. 그 전까지 팀원에게는 저장소의 `docs/wiki/` 문서 링크를 준다.
