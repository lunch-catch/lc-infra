# 팀원 도메인 모니터링

자기 도메인에 지표, 로그, 대시보드를 붙이고 로컬에서 확인하는 순서를 적는다 (lc-infra #64). 본보기는 07 광고 서빙 대시보드(`observability/grafana/dashboards/07-adserving.json`)다.

부하 시험 환경에서 이 대시보드로 시험을 보는 순서는 [팀원 부하 시험 가이드](./팀원-부하시험-가이드.md)가 갖는다.

## 1. 이미 되는 것

수집은 도메인을 가리지 않는다. 아래는 도메인이 따로 할 일이 없다.

| 항목 | 내용 |
|---|---|
| 앱 지표 수집 | Prometheus 가 앱과 배치 서버의 `/actuator/prometheus` 를 통째로 긁는다. 새 지표도 코드에 넣으면 들어온다 |
| 로그 수집 | Alloy 가 컨테이너 로그를 통째로 Loki 에 민다. 라벨은 `container`, `role`(`app`, `batch`), `git_sha` 다 |
| API 별 응답 시간 | lc-backend 의 `application.yml` 이 HTTP 요청 히스토그램을 앱 전체에 켠다. 새 엔드포인트도 05 부하 시험의 API 별 p99 에 나온다 |
| 대시보드 반영 | `grafana/dashboards/*.json` 을 프로비저닝이 30초마다 다시 읽는다 |

## 2. 도메인이 할 일

### 2.1 지표

이름과 태그는 lc-backend 의 `docs/software-quality/qa-observability-guideline.md` 2장을 따른다. 태그에 ID, 이메일, URL 원문을 넣지 않는다.

이름은 `{도메인}_{대상}_{결과}_total` 꼴로 쓴다. 07 의 `adserving_impression_dropped_total` 이 그 꼴이다.

**여러 도메인에 같은 뜻으로 있는 것은 공통 이름에 꼬리표로 나눈다.** 같은 것을 여러 곳에서 재면 이름을 하나로 두고 어디서 쟀는지를 꼬리표에 둔다. 그러면 쿼리 하나로 모두 그리고, 새로 생겨도 대시보드를 고치지 않는다. 아웃박스 릴레이와 비동기 워커의 밀린 양이 그렇다. 06 기준 초과가 이 이름으로 그린다(lc-backend #1131).

| 대상 | 지표 | 꼬리표 |
|---|---|---|
| `@Scheduled` 작업의 실행 시간 | `batch_job_duration_seconds` | `scheduler` |
| 아웃박스 릴레이의 미발행 건수와 가장 오래 기다린 건의 대기 시간 | `outbox_relay_backlog`, `outbox_relay_oldest_age_seconds` | `relay` |
| 비동기 워커의 대기열 길이와 가장 오래 기다린 일의 대기 시간 | `async_worker_queue_size`, `async_worker_oldest_age_seconds` | `worker` |

`relay` 와 `worker` 의 값은 기준 규칙(`observability/prometheus/thresholds.yml`)의 `name` 과 같게 쓴다. 예: `adserving.impression`. 버린 수나 결과별 횟수처럼 도메인 뜻이 있는 지표는 도메인 이름 그대로 둔다.

**카운터는 기동 때 0 으로 등록한다.** Micrometer 는 처음 증가할 때 카운터를 만든다. 그 전에는 지표가 없어 패널이 "No data" 를 보인다. 첫 증가도 `rate` 가 잡지 못한다. 생성자에서 한 번 만들어 두면 0 부터 그려진다.

```java
static final String FAILED_METRIC = "billing_deduct_failed_total";

public DeductService(MeterRegistry meterRegistry) {
    this.meterRegistry = meterRegistry;
    meterRegistry.counter(FAILED_METRIC);
}
```

### 2.2 로그

lc-backend 의 `docs/code-convention/logging-project-guideline.md` 를 따른다. 실패는 `event={도메인}_{대상}_FAILED key=value` 로 남기고 수준을 WARN 이나 ERROR 로 정한다.

**이벤트 이름을 바꾸면 그 이름을 쓰는 대시보드와 경보를 함께 고친다.** 같은 문서의 근거(`logging-project-rationale.md` 12장)가 정한 규칙이다. 대시보드는 이 저장소에 있어 lc-backend 의 PR 만 보면 놓친다. 광고 서빙 대시보드(지금 07)의 경고 로그 패널이 그렇게 비었다(#62).

### 2.3 대시보드

07 광고 서빙을 복사해 시작한다. 화면에서 고친 것은 저장되지 않는다(`allowUiUpdates: false`). 화면에서 패널을 만들었으면 "Export -> Export as JSON" 으로 받아 파일에 넣는다.

| 항목 | 정한 값 |
|---|---|
| 파일 | `observability/grafana/dashboards/{번호}-{도메인}.json` |
| `uid` | `lc-{도메인}`. 캡처 스크립트와 링크가 이 값으로 대시보드를 찾는다 |
| 데이터 소스 | `uid` 로 적는다. Prometheus 는 `prometheus`, Loki 는 `loki` 다 |
| 새로고침 | `30s` |
| 카운터 패널 | `rate(...[$__rate_interval]) * 60` 으로 분당 수를 그린다. 제목 끝에 `(분당)` 을 붙인다 |
| 배치 서버에서만 도는 일의 지표 | `job="batch"` 로 고른다. 앱 서버도 같은 이름의 지표를 0 으로 내보낼 수 있어 섞이지 않게 한다 |

**경고 로그 패널.** 07 의 쿼리에서 도메인 접두사만 바꾼다. 이름의 끝이 아니라 로그 수준으로 골라 이름이 다른 경고도 걸린다.

```
{container=~"lunchcatch.*", role=~"app|batch"} |~ "event=BILLING_" | json | level=~"WARN|ERROR" | line_format "{{.message}}"
```

`line_format` 이 한 줄에 `message` 만 남긴다. 스택 트레이스는 Explore 에서 `line_format` 을 빼고 본다.

### 2.4 경보

`observability/prometheus/rules.yml` 에 규칙을 더하고 `rules_test.yml` 에 시험을 더한다. 시험은 `rules_test.yml` 맨 위의 `promtool` 명령으로 돌린다. 임계값은 부하 시험에서 읽은 값으로 정하고 지어내지 않는다.

### 2.5 부하 시험 캡처

`scripts/loadtest-snapshot.sh` 의 기본 목록(`DASH=(...)`)에 `lc-{도메인}` 을 더한다. 한 번만 찍을 때는 `--dash lc-{도메인}` 으로 준다.

## 3. 로컬에서 확인

`observability/local/compose.yaml` 이 앱, MySQL, Valkey 와 관측 스택을 함께 띄운다. 관측 스택은 Prometheus, Grafana, Loki, Alloy, 캡처용 렌더러와 수집기 넷(node, cAdvisor, mysqld, redis)이고 운영과 같은 태그와 설정 파일을 쓴다. 대시보드는 이 작업 트리의 JSON 을 그대로 읽는다.

부하 시험 환경과 대시보드, 수집 대상이 같아 같은 화면으로 동작을 확인한다. 다만 노트북은 서버 크기와 대수가 달라 수치는 부하 시험 환경에서 잰다.

**한 번 준비한다.** 이 폴더의 `.env` 에 시험용 비밀값과 lc-backend 경로를 둔다. `.env` 는 커밋되지 않는다.

```bash
cd observability/local
printf 'JWT_SECRET=%s\nLC_BACKEND_DIR=%s\n' "$(openssl rand -base64 48)" <lc-backend 경로> > .env
```

**띄운다.** 앱 이미지는 lc-backend 의 jar 를 담기만 하므로 jar 를 먼저 만든다.

```bash
(cd <lc-backend 경로> && ./gradlew bootJar -x test)
docker compose up -d --build
```

| 주소 | 무엇 |
|---|---|
| http://localhost:13000 | Grafana (`admin` / `admin`) |
| http://localhost:18080 | 앱 |
| http://localhost:19090 | Prometheus |

포트가 겹치면 `.env` 에 `GRAFANA_PORT`, `APP_PORT`, `PROMETHEUS_PORT` 를 둔다.

**확인한다.**

1. Prometheus 의 Status -> Targets 에서 `app`, `batch`, `node`, `cadvisor`, `mysqld`, `redis` 가 UP 인지 본다
2. 도메인 대시보드에서 지표 패널이 "No data" 가 아니라 0 부터 그려지는지 본다. "No data" 면 2.1 의 0 등록이 빠졌다
3. 실패를 일부러 만들고 경고 로그 패널에 그 로그가 찍히는지 본다. 의존하는 저장소를 잠깐 멈추면 된다

```bash
docker compose pause valkey; sleep 10; docker compose unpause valkey
```

**캡처한다.** 부하 시험 환경과 같은 스크립트를 `--local` 로 돌린다. 터널 없이 이 그라파나의 여섯 장을 대시보드 높이 그대로 찍는다.

```bash
./scripts/loadtest-snapshot.sh --local --label <이름> --minutes 5
```

JSON 을 고치면 30초 안에 Grafana 가 다시 읽는다. 앱 코드를 고쳤으면 jar 를 다시 만들고 `docker compose up -d --build app` 을 돌린다.

**내린다.** DB 와 로그는 컨테이너와 함께 지워진다.

```bash
docker compose down
```

DB 는 빈 채로 뜬다. 데이터를 넣고 부하를 거는 법은 lc-backend 의 `loadtest/README.md` 를 따른다.

맥의 Docker Desktop 에서는 cAdvisor 가 컨테이너 이름을 읽지 못해 02 호스트의 컨테이너 메모리 패널이 빈다. CloudWatch 패널(ALB, CPU 크레딧, RDS)은 로컬에 원천이 없어 빈다.

## 4. 운영에 반영

PR 이 `main` 에 병합되면 모니터링 서버에서 `git pull` 한다. 대시보드는 30초 안에 바뀐다. 경보 규칙은 Prometheus 를 재시작해야 바뀐다. 절차는 `observability/README.md` 의 첫 절을 따른다.
