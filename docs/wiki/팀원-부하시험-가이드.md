# 팀원 부하 시험 가이드

백엔드 팀원이 자기 AWS 계정으로 부하 시험 환경을 띄우고, 시험을 돌리고, 그라파나로 보고, 결과를 남기고, 내리는 순서다(lc-infra #92). **이 문서는 순서만 갖는다.** 단계마다의 명령과 설명은 그것을 가진 문서로 간다.

| 단계의 자세한 내용 | 가진 문서 |
|---|---|
| 계정 준비, 환경 띄우기와 내리기, 비용, 막힐 때 | [팀원 부하 시험 환경](./팀원-부하시험-환경.md) |
| 내 도메인에 지표, 로그, 대시보드 붙이기, 로컬 관측 구성 | [팀원 도메인 모니터링](./팀원-도메인-모니터링.md) |
| 공용 실행 스크립트, 로컬 실행, 프로파일링, 추적 | lc-backend [`loadtest/README.md`](https://github.com/lunch-catch/lc-backend/blob/develop/loadtest/README.md) |
| 한 도메인의 시험 조건과 돌리는 순서(본보기) | lc-backend [`adserving_부하_시험.md`](https://github.com/lunch-catch/lc-backend/blob/develop/docs/design/adserving/loadtest/adserving_부하_시험.md) |

## 1. 한눈에 보기

```
처음 한 번   계정 준비 ─┐
시험마다     로컬에서 먼저 ─> 환경 띄우기 ─> 데이터와 회차 ─> 그라파나로 보기 ─> 깊이 보기(필요할 때) ─> 결과 남기기 ─> 내리기
도메인마다   실행 스크립트와 대시보드를 한 번 만든다
```

| 단계 | 하는 곳 | 걸리는 시간 |
|---|---|---|
| 계정 준비 | AWS 콘솔, 내 노트북 | 처음 한 번. vCPU 한도를 올려야 하면 하루쯤 |
| 로컬에서 먼저 | lc-infra `observability/local`, lc-backend | 30분쯤 |
| 환경 띄우기 | lc-infra `scripts/member-env.sh up` | 처음은 25분쯤 |
| 데이터와 회차 | lc-backend `loadtest/{도메인}/run.sh` | 회차마다 10분 안팎 |
| 내리기 | lc-infra `scripts/member-env.sh down` | 10분쯤 |

켜 둔 동안 내 계정으로 시간당 약 0.4~0.6 USD 가 나간다. 잊을 것 같으면 `MEMBER_HOURS` 를 준다([환경 문서 4절](./팀원-부하시험-환경.md#4-비용)).

## 2. 처음 한 번: 계정 준비

자기 AWS 계정, 관리자 IAM 사용자와 CLI 프로필, AWS CLI, Terraform, Session Manager 플러그인을 갖추고 EC2 vCPU 한도를 확인한다. 목록과 명령은 [환경 문서 2절](./팀원-부하시험-환경.md#2-준비-한-번)이 갖는다.

## 3. 도메인마다 한 번: 실행 스크립트와 대시보드

| 할 일 | 가진 문서 |
|---|---|
| `loadtest/{도메인}/` 에 시나리오, 데이터 생성기, `run.sh` 를 둔다. `run.sh` 는 공용 스크립트(`loadtest/lib/common.sh`)를 불러 쓰고 그 도메인의 로그 접두사, 결과 문서, 더 물을 지표만 정한다 | lc-backend `loadtest/README.md` 의 [실행 스크립트의 공통 부분](https://github.com/lunch-catch/lc-backend/blob/develop/loadtest/README.md#실행-스크립트의-공통-부분) |
| 시험 조건(데이터, 회차, 통과 기준)과 돌리는 순서를 도메인의 부하 시험 문서에 적는다 | 본보기: [`adserving_부하_시험.md`](https://github.com/lunch-catch/lc-backend/blob/develop/docs/design/adserving/loadtest/adserving_부하_시험.md) |
| 도메인 지표와 로그를 붙이고 대시보드를 만든다. 캡처 목록에도 더한다 | [모니터링 문서 2절](./팀원-도메인-모니터링.md#2-도메인이-할-일) |

## 4. 로컬에서 먼저

AWS 를 띄우기 전에 같은 명령을 노트북에서 돌려, 시나리오와 대시보드가 맞는지 본다. `run.sh` 의 첫 인자로 `--local` 을 주면 lc-infra 의 로컬 구성을 대상으로 같은 인자로 돈다. 수치는 노트북의 것이라 결과 문서에 적지 않는다.

- 로컬 구성 띄우기: [모니터링 문서 3절](./팀원-도메인-모니터링.md#3-로컬에서-확인)
- 로컬에서 돌리는 순서: lc-backend `loadtest/README.md` 의 [로컬에서 돌리기](https://github.com/lunch-catch/lc-backend/blob/develop/loadtest/README.md#로컬에서-돌리기)

## 5. 환경 띄우기

lc-infra 를 최신으로 받고 `AWS_PROFILE=<내 프로필> ./scripts/member-env.sh up` 을 돌린다. 예전 커밋으로 띄우려면 `up --sha <커밋>` 이다. 띄운 뒤 `status` 가 그라파나 접속 방법을 보여 준다. 명령과 옵션은 [환경 문서 3절](./팀원-부하시험-환경.md#3-쓰는-법)이 갖는다.

## 6. 데이터와 회차

lc-backend 에서 같은 프로필로 도메인의 `run.sh` 를 돌린다. 데이터 넣기, 그날 준비, 워밍업, 측정 회차 순서와 회원 대역은 도메인의 부하 시험 문서가 정한다(본보기: `adserving_부하_시험.md` 6장).

**시험용 브랜치에서 돌린다.** 회차가 끝나면 `run` 이 그 회차의 경고와 오류를 이벤트별로 세어 결과 문서에 적고 **지금 브랜치에 커밋한다.** `develop` 에서 돌리면 `develop` 에 커밋이 생긴다. 푸시는 하지 않는다. 워밍업(`-warmup`), 프로파일링(`-profile`), 추적(`-tracing`) 회차는 적지 않는다.

`run` 은 끝날 때 두 구간을 밀리초로 출력한다. 다음 단계의 지표와 캡처가 이 두 줄을 쓴다.

| 줄 | 뜻 | 쓰는 곳 |
|---|---|---|
| `window <시작> <끝>` | 회차 전체. 램프업을 포함한다 | `run.sh metrics <window 시작 ms> <window 끝 ms>`, 캡처의 `--from` |
| `hold <시작> <끝>` | 결과를 세는 유지 구간 | 캡처의 `--to`(유지 구간의 끝) |

## 7. 그라파나로 보기

`status` 가 보여 주는 포트 포워딩을 연 동안 `http://localhost:13000` 에서 본다. 운영과 같은 대시보드가 들어 있다.

| 대시보드 | 보는 것 |
|---|---|
| 01 서비스 개요 | 상태 코드별 요청률, 5xx 비율, 응답 분위수, 느린 엔드포인트 상위 5개(p99), ALB 가 잰 응답 시간 |
| 02 호스트 | 서버마다 CPU, 메모리, 네트워크 |
| 03 앱과 JVM | DB 커넥션 풀, 톰캣 스레드, 힙, GC, 종류별 스레드 |
| 04 데이터 저장소 | MySQL, Valkey |
| 05 부하 시험 | k6 가 본 요청률, 응답 지연, 실패, VU |
| 06 처리 시간 목표 초과 | 기준을 넘은 API 와 백그라운드 작업을 고르고 트레이싱과 프로파일로 넘어간다. 트레이싱과 프로파일링을 켠 회차에서 채워진다 |
| 07 이후 | 도메인 대시보드(07 광고 서빙, 08 정산과 분석). 그 도메인의 경고와 오류 로그 패널이 있다 |

- **결과 수치는 k6 요약과 `run.sh metrics` 에서 읽는다.** 대시보드는 그 수치가 왜 나왔는지(무엇이 먼저 올랐는지, 유지 구간이 안정됐는지)를 보는 흐름이다.
- 05 의 응답 지연은 부하 생성기가 본 시간이고, 01 의 느린 엔드포인트 p99 는 앱이 잰 시간이다. 앞이 크면 그 차이가 앱 앞에서 기다린 시간이다.
- 그 회차의 경고와 오류 원문은 Explore 에서 `Loki` 를 고르고 찾는다. 건수는 6절의 커밋으로 결과 문서에 남는다.

## 8. 깊이 보기: 프로파일링과 추적

느린 원인이 지표로 가려지지 않을 때 쓴다. **측정 회차와 나눈다.** 표본과 스팬을 만드는 비용이 응답 시간에 섞인다.

| 도구 | 보는 것 | 그라파나에서 | 켜는 법 |
|---|---|---|---|
| 프로파일링 | 어느 코드가 CPU 와 기다림에 시간을 썼나(합계) | Drilldown -> Profiles, 서비스 `lunchcatch` | lc-backend `loadtest/README.md` 의 [프로파일링](https://github.com/lunch-catch/lc-backend/blob/develop/loadtest/README.md#프로파일링) |
| 추적 | 느린 요청 하나가 어느 단계에서 몇 ms 를 썼나 | Explore -> `Tempo`. 로그의 `trace_id` 에서도 넘어간다 | lc-backend `loadtest/README.md` 의 [추적](https://github.com/lunch-catch/lc-backend/blob/develop/loadtest/README.md#추적) |

두 저장소(Pyroscope, Tempo)는 부하 시험 환경에서만 뜬다(lc-infra #71, #72).

## 9. 결과 남기기

`down` 하면 Prometheus, Loki, Pyroscope, Tempo 의 기록이 함께 사라진다. **내리기 전에** 남긴다.

| 남길 것 | 방법 |
|---|---|
| 대시보드 PNG | lc-infra 에서 `AWS_PROFILE=<내 프로필> ./scripts/loadtest-snapshot.sh --lt --label <회차> --from <window 시작 ms> --to <hold 끝 ms>`. 자세한 옵션은 [환경 문서 3절](./팀원-부하시험-환경.md#3-쓰는-법) |
| 수치와 해석 | 도메인의 결과 문서. 자리와 태그 규칙은 도메인의 부하 시험 문서가 정한다(본보기: `adserving_부하_시험.md` 8장) |
| 경고 로그 건수 | 6절의 커밋이 이미 남겼다. 시험용 브랜치를 푸시해 PR 로 올린다 |

## 10. 내리기

`AWS_PROFILE=<내 프로필> ./scripts/member-env.sh down` 을 돌린다. `MEMBER_HOURS` 로 자동 정리됐어도 남은 것이 있어 한 번 부른다([환경 문서 3절](./팀원-부하시험-환경.md#3-쓰는-법)).
