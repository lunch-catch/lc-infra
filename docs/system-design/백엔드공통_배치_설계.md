# 배치 설계 (백엔드 공통)

주기 실행 배치를 전용 서버 두 대에서 액티브-액티브로 돌린다. 그 인프라 구성과, 배치가 다시 돌아도 데이터가 깨지지 않게 하는 장치를 적는다.

애플리케이션 쪽 규칙(점유, 생존 신호, 이어받기, 자동 재실행)은 backend 의 `docs/architecture/런치캐치_배치_운영.md` 가 갖는다. 이 문서는 그 규칙이 기대는 인프라를 적고, 규칙 자체는 옮겨 적지 않는다.

이전 구성은 배치 서버 한 대에 분산 락 없이 "프로세스는 항상 하나" 를 전제로 했다. 2026-10-06 에 두 대로 바꾸면서 그 전제를 버렸고, 중복 실행은 서버 수가 아니라 DB 점유로 막는다. 바뀐 이유는 2.1 절에 있다.

## 2. 배치 서버

### 2.1 목적과 두 대인 이유

주기 실행 스케줄러를 돌린다. 영업일 경계(00:00) 작업 묶음, 캠페인별 쿠폰 만료, 생존 신호, 이어받기가 여기서 돈다.

앱과 분리한 이유는 **스케줄러가 도는 곳을 앱 대수와 무관하게 정하기 위해서**다.
Spring 의 `@Scheduled` 는 인스턴스마다 독립적으로 도므로, 앱 안에 두면 앱을 늘릴 때 배치도 함께 늘어난다.

두 대를 두는 이유는 **00:00 에 장애가 나도 사람이 넘기지 않게 하기 위해서**다.
한 대일 때는 그 서버가 죽으면 영업일 경계 작업이 사람이 손댈 때까지 멈췄고, 서버가 죽으면 지표도 함께 사라져 알람조차 울리지 않았다.

두 대 모두 스케줄러를 켜고 같은 시각에 같은 작업을 시도한다. 중복 실행은 서버 수로 막지 않고 DB 로 막는다.

```
작업 시작   batch_execution_log 에 RUNNING 행을 넣는다. UNIQUE (job_name, business_date)
            -> 먼저 넣은 서버만 실행한다. 나머지는 건너뛴다
실행 중     30초마다 자기 행의 updated_at 을 갱신한다 (생존 신호)
멈추면      다른 서버가 updated_at 이 2분보다 오래된 행을 조건부 UPDATE 로 가져가 이어서 실행한다
```

판정은 전부 조건부 UPDATE 의 바뀐 행 수로 한다. 읽고 나서 판단하면 두 서버가 같은 상태를 읽고 둘 다 자기 것이라고 믿는 구간이 생긴다. 상세는 backend 문서 2장과 3장이다.

### 2.2 구성

| 항목 | 값 | 코드 |
|---|---|---|
| 형태 | 시작 템플릿 + ASG. min, max, desired 모두 2 | `terraform/compute.tf` `aws_autoscaling_group.batch` |
| 위치 | 사설 서브넷 AZ a, c 에 한 대씩. ASG 가 AZ 균형을 맞춘다 | 같은 곳 |
| 인스턴스 | `t3.small`, x86. 앱과 같은 이미지를 받기 때문이다 | `variables.tf` `instance_types` |
| 인바운드 | 모니터링에서 오는 8081, 9100, 8082 뿐. ALB 에 붙지 않는다 | `security.tf` |
| 운영 접근 | SSM Session Manager | |
| 산출물 | 앱과 같은 jar | |
| 구분 | `SPRING_PROFILES_ACTIVE=prod,batch` | `compute.tf` `batch_user_data` |
| 스케줄러 스위치 | SSM `/<project>/batch-scheduler-enabled` -> `LAUNCHCATCH_SCHEDULER_ENABLED`. 배치 컨테이너에만 넘긴다 | `ssm.tf`, `templates/compose.yaml.tftpl` |
| 시각 | Amazon Time Sync (169.254.169.123) | `templates/app-user-data.sh.tftpl` |
| 서버 식별자 | 주지 않는다 | |
| 헬스체크 | EC2 상태 검사 | |

스케줄러는 `application-batch.yml` 의 `launchcatch.scheduler.enabled: true` 로만 켜진다. 앱 인스턴스는 `batch` 프로필이 없으므로 스케줄러가 없다. **앱을 몇 대로 늘려도 스케줄러는 배치 서버에서만 돈다.**

**스케줄러 스위치를 SSM 에 두는 이유**는 `.env` 가 배포와 재시작마다 `refresh-env` 로 통째로 다시 쓰이기 때문이다. 인스턴스에서 손으로 고친 값은 다음 배포에 사라진다. 끄는 절차는 `docs/deploy/README.md` 에 있다.

**시각을 맞추는 이유**는 두 서버가 `updated_at` 2분으로 서로의 생존을 판정하기 때문이다. 시계가 어긋나면 멀쩡히 일하는 서버의 작업을 빼앗거나 영업일 경계를 다르게 본다. 링크 로컬 주소라 NAT 를 거치지 않는다.

**서버 식별자(`LAUNCHCATCH_BATCH_OWNER_ID`)를 주지 않는 이유**는 고정값이 위험하기 때문이다. 인스턴스 ID 처럼 재시작해도 같은 값을 주면, 프로세스가 죽고 다시 뜬 뒤 새 프로세스의 생존 신호가 죽은 프로세스의 행까지 갱신한다. 그 행은 영원히 살아 있는 것처럼 보여 아무도 이어받지 않는다. 주지 않으면 앱이 호스트 이름에 임의 접미사를 붙여 프로세스마다 다르게 만든다.

**대수는 고정이다.** 스케일링 정책이 없다. 배치는 부하에 따라 늘릴 일이 없고, 늘려도 점유 경쟁만 는다.

jar 를 나누지 않은 이유는 배치가 앱과 같은 엔티티와 Service 를 쓰기 때문이다. 00:00 작업 순서가 여러 도메인에 걸쳐 한 프로세스 안에서 이어진다. backend 의 `런치캐치_도메인_구조와_의존성_설계.md` 2.4 절이 근거다.

### 2.3 교체와 배포

**모든 교체를 한 대씩 한다.** 한 대가 내려가 있는 동안 다른 한 대가 작업을 맡는다. 둘을 한꺼번에 내리면 그 사이 00:00 묶음이 비고, 실행 중이던 작업을 이어받을 서버도 없다.

| 계기 | 방법 |
|---|---|
| 애플리케이션 배포 | `deploy.sh` 10단계가 서버마다 `refresh-env` 와 서비스 재시작을 차례로 건다. 한 대가 실패하면 나머지는 건드리지 않고 멈춘다 |
| 템플릿(user-data) 변경 | ASG instance refresh. `min_healthy_percentage = 50` 이라 두 대 중 한 대씩 바뀐다 |
| AMI 갱신 | 무시한다. 시작 템플릿에 `ignore_changes = [image_id]`. 무관한 apply 가 배치를 교체하지 않게 한다 |
| 세션 중지와 재가동 | `stop.sh` 가 min 과 desired 를 0 으로, `start.sh` 가 2 로 둔다. `stop-instances` 를 쓰면 ASG 가 교체한다 |

**잠시 구버전과 신버전 배치가 함께 돈다.** 같은 작업을 동시에 시도해도 유일 제약이 한쪽만 통과시키므로 중복 실행은 없다. 대신 어느 버전이 점유할지는 알 수 없으므로 상태 전이는 두 버전 모두에서 안전해야 한다(4장).

**앱보다 뒤에 교체한다.** 스키마 확장 후 축소 때문이다. 앱이 먼저 새 버전이 되어야 배치가 새 스키마를 전제해도 안전하다.

### 2.4 장애가 나면

| 장애 | 결과 | 알림 |
|---|---|---|
| 앱 프로세스가 죽음 | Docker 가 되살린다. 새 프로세스는 새 식별자를 받아 2분 뒤 죽은 프로세스의 행을 이어받는다 | 반복되면 `ContainerRestartLoop` |
| 인스턴스가 죽음 | 다른 한 대가 2분 안에 이어받는다. ASG 가 새 인스턴스로 교체한다 | 5분 뒤 `BatchDegraded` |
| AZ 장애 | 남은 AZ 의 배치가 계속 돈다. ASG 가 남은 AZ 에 대체 인스턴스를 띄운다 | 같음 |
| 두 대 모두 죽음 | 영업일 경계 작업이 돌지 않는다. ASG 가 교체를 시도한다 | 3분 뒤 `BatchAllDown` (critical) |
| 모니터링도 함께 죽음 | 위와 같다 | CloudWatch `batch-capacity` 와 `monitoring-status` (이메일) |
| 스케줄러만 멈춤 | 프로세스는 살아 있으나 작업이 돌지 않는다 | `BatchNotRun` |

배치 서버가 모두 멈춰도 피드, 노출 차감, 쿠폰 발급은 API 서버에서 계속 처리된다.

### 2.5 알람

| 알람 | 어디 | 조건 | 왜 |
|---|---|---|---|
| `BatchDegraded` | Prometheus | 살아 있는 배치 < 2, 5분 | 한 대가 죽어도 작업은 돈다. 그래서 알리지 않으면 두 번째 장애 때 처음 안다. 5분은 배포의 한 대씩 재시작을 넘기기 위해서다 |
| `BatchAllDown` | Prometheus | 살아 있는 배치 0, 3분 | `absent` 로 대상이 모두 사라진 경우도 잡는다 |
| `BatchNotRun` | Prometheus | 마지막 성공 시각이 주기를 넘김. 00:00 묶음 25시간, 나머지 30분 | 프로세스는 살아 있는데 스케줄러가 멈춘 경우다. 서버가 죽은 경우는 못 잡는다. 지표가 함께 사라지기 때문이다 |
| `batch-capacity` | CloudWatch | ASG InService < 2, 10분 | 모니터링이 함께 죽어도 알린다. 단일 지표라(`INF-12-14`) `stop.sh` 로 내리면 울리므로 `stop.sh` 가 알림을 끄고 `start.sh` 가 켠다. 10분은 ASG 교체 시간이다 |

`BatchNotRun` 만으로 부족했던 것이 한 대 구성의 공백이었다. 서버가 죽으면 성공 시각 지표가 사라져 비교할 값이 없고, 그래서 서버가 죽은 것을 아무도 몰랐다. 수집 대상이 살아 있는지를 따로 보는 앞의 둘이 그 자리를 채운다.

## 3. 배치 유형과 재실행 안전성

DB 점유가 있어도 유형 분류는 그대로 필요하다.
**배치가 중간에 죽고 다시 도는 것은 점유와 무관하게 일어나기 때문이다.** 배포, 인스턴스 교체, 예외, 이어받기가 전부 그 경로다. 특히 이어받기는 멈춘 단계를 처음부터 다시 돈다.

### 3.1 배치 유형별 중복 실행 피해

연산의 성격에 따라 재실행 위험이 전혀 다르다. 무해한 것과 치명적인 것을 같은 방식으로 다루면 둘 다 잘못된다.

| 유형 | 연산 성격 | 다시 돌면 | 심각도 | 멱등화 필요 |
|------|-----------|--------------|--------|---------|
| 멱등 전이형 | 상태를 특정 값으로 덮어씀 | 같은 결과. 무해 | 낮음 | 불필요 |
| 재계산형 | 원본에서 값을 다시 계산해 덮어씀 | 같은 결과. 자원 낭비만 | 낮음 | 선택 |
| 누적 연산형 | 수량이나 잔액을 증감 | **오차가 누적되어 남음** | 치명적 | 필수 |
| 외부 부수효과형 | 알림 발송, 결제 요청, 파일 전송 | 외부에 이중 요청 | 높음 | **멱등화로 못 막는다** |
| 순번 발급형 | 시퀀스나 채번 | 번호 중복 또는 건너뜀 | 높음 | 필수 |

예시로 옮기면 이렇다.

| 배치 예시 | 유형 | 중복 시 결과 |
|---|---|---|
| 만료 상태 일괄 전이 (`status = EXPIRED`) | 멱등 전이형 | 무해 |
| 통계 집계 테이블 갱신 | 재계산형 | 무해, CPU 낭비 |
| 만료 처리 후 자원 반환 (수량, 좌석, 한도 복원) | 누적 연산형 | **반환이 두 번 일어나 값이 부풀려짐** |
| 확정 처리 후 적립금 지급 | 누적 연산형 | **이중 지급** |
| 미발송 알림 재시도 | 외부 부수효과형 | 중복 발송 |
| 정산 번호 채번 | 순번 발급형 | 번호 충돌 |

**핵심은 세 번째 행이다.** 상태 전이만 보면 두 번 다 같은 값이라 무해해 보이지만, 그 전이에 딸린 누적 연산은 두 번 실행되면 그만큼 값이 커진다.

이 오차는 **발생 시점에 아무 신호도 내지 않는다.** 예외도, 오류 로그도, 실패 응답도 없다. 증상은 며칠 뒤 무관해 보이는 다른 트랜잭션에서 나타난다.

```
14:00  배치 중복 실행으로 자원 수량이 +3 부풀려짐
14:00  오류 없음. 예외 없음. 로그 정상
       사용자 화면에는 3개가 더 있는 것으로 표시됨
       ... 며칠간 정상 거래 계속 ...
17:20  그 3개를 소비하려는 요청이 실패
17:20  "자원 부족" 오류  <- 원인을 가리키지 않는 증상
```

원인이 발생한 시점과 증상이 나타난 시점이 멀고, 증상의 형태가 원인과 달라 추적이 매우 어렵다. **이 시간차가 곧 복구 난이도다.** 사고 직후면 되돌릴 수 있지만, 며칠 지나면 그 사이 정상 거래가 쌓여 되돌릴 방법이 사실상 없어진다.

감지 수단은 백업과 복원 문서 8절의 정합성 검증 배치이며, 대응 절차는 알람과 알림 설계 문서 5.4절에 있다.

### 3.2 피해 시나리오 상세

만료 처리 후 자원을 반환하는 배치를 예로 든다. 흐름은 세 단계다.

1. 만료 조건에 해당하는 레코드를 찾는다
2. 상태를 `EXPIRED`로 바꾼다
3. 점유했던 자원(수량, 좌석, 한도 등)을 되돌린다

무엇이든 배치를 두 번 돌게 만들면 다음과 같이 흐른다. 이어받기, 프로필 설정 실수, 수동 재실행이 그 경로다.

```
시각  인스턴스 A                       인스턴스 B
t0    레코드 1001 조회 (PENDING)       레코드 1001 조회 (PENDING)
t1    status = EXPIRED 로 갱신
t2                                      status = EXPIRED 로 갱신 (덮어쓰기, 무해해 보임)
t3    자원 풀에 수량 + 3
t4                                      자원 풀에 수량 + 3
```

자원 수량이 실제보다 3만큼 부풀려진다. 상태만 보면 이상이 없어 검증 쿼리로도 잡히지 않는다.

## 4. 최종 방어선: 조건부 UPDATE 멱등화

배치가 중복으로 돌거나 중간에 죽고 다시 돌아도 데이터가 깨지지 않게 하려면,
상태 전이를 원자적 조건부 UPDATE 로 수행하고 그 결과로 이후 동작을 분기해야 한다.

```java
@Transactional
public void expire(long recordId, Instant now) {
    // 상태 전이를 조건부 UPDATE 로 수행한다.
    // 이미 다른 인스턴스가 처리했다면 affected rows 는 0 이 된다.
    int transitioned = jdbcTemplate.update("""
            UPDATE reservation
               SET status = 'EXPIRED', updated_at = ?
             WHERE id = ? AND status = 'PENDING'
            """, Timestamp.from(now), recordId);

    if (transitioned == 0) {
        return;   // 누적 연산도 하지 않고 즉시 종료한다.
    }

    statusHistoryRepository.append(recordId, Status.EXPIRED, ChangedBy.BATCH);
    resourceService.release(recordId);   // 자원 반환은 전이에 성공한 쪽만 수행
}
```

핵심은 세 가지다.

1. **조회 후 판단하지 않는다.** `if (record.getStatus() == PENDING)` 형태로 먼저 확인하고 나중에 갱신하면 그 사이에 다른 인스턴스가 끼어든다. 갱신 손실 패턴 그대로다.
2. **누적 연산을 전이 성공 여부에 종속시킨다.** 전이가 원자적인 한, 누적 연산도 정확히 한 번 일어난다.
3. **전이와 누적 연산이 같은 트랜잭션 안에 있다.** 전이만 커밋되고 반환이 실패하면 자원이 영영 돌아오지 않는다.

외부 부수효과형 배치는 조건부 UPDATE로 먼저 처리 중 상태를 선점한 뒤 외부를 호출한다.

```java
// 발송 전에 상태를 선점한다. 선점에 실패하면 다른 인스턴스가 이미 집어 든 것이다.
int claimed = jdbcTemplate.update("""
        UPDATE notification
           SET status = 'SENDING', claimed_at = ?
         WHERE id = ? AND status IN ('PENDING', 'RETRY')
        """, Timestamp.from(now), notificationId);

if (claimed == 0) {
    return;
}
channel.send(notificationId);
```

발송 후에 상태를 바꾸면 그 사이에 다른 인스턴스가 같은 행을 집어 든다. 순서가 반대여야 한다.

## 5. 전제가 깨졌을 때

스케줄러가 배치 서버에서만 돈다는 전제는 **시작 템플릿의 문자열 하나**에 걸려 있다.
앱 ASG 에 실수로 `batch` 프로필이 들어가면 앱 대수만큼 스케줄러가 돈다.

DB 점유가 있으므로 같은 작업이 두 번 실행되지는 않는다. 그러나 앱 인스턴스가 점유 경쟁에 끼어들어, 스케일 인으로 종료되는 앱이 묶음을 쥐고 있다가 끊기거나 요청 처리와 배치가 같은 커넥션 풀을 다툰다. 점유가 막는 것은 중복 실행뿐이다.

두 층으로 받는다.

### 5.1 예방: Terraform

시작 템플릿의 user-data 를 코드로 고정한다. 콘솔에서 손으로 바꾸는 경로를 없앤다.
스케줄러 스위치(`LAUNCHCATCH_SCHEDULER_ENABLED`)도 compose 템플릿이 `role` 이 `batch` 일 때만 컨테이너에 넘긴다. 앱에 넘기면 그쪽 스케줄러가 켜질 길이 생긴다.

**Terraform 코드 자체가 틀린 경우는 못 막는다.** 코드가 진실이므로 잘못 쓰면 그대로 배포된다. 그래서 `INF-12-07` 이 앱 시작 템플릿에 `batch` 프로필이 없는지를 판정한다.

### 5.2 탐지

원인을 가리지 않고 결과를 잡는다.

| 지표 | 정의 | 수집 방법 |
|------|------|-----------|
| 실행 주체 | `batch_execution_log.owner_id` 가 배치 서버가 아님 | 조회 |
| 배치 미실행 | 2.5 절의 알람 넷 | Prometheus, CloudWatch |

탐지가 예방보다 중요한 이유가 있다. 조건부 UPDATE 멱등화가 데이터 손상은 막지만,
**외부 부수효과형은 못 막는다.** 이미 나간 알림은 되돌릴 수 없다. 그래서 났는지 아는 것이 먼저다.
