## 2. 왜 도메인을 샀나

Vercel 은 HTTPS 로만 서비스한다. 도메인이 없을 때 백엔드 ALB 는 HTTP 뿐이었다. 길은 셋이었다.

| 길 | 동작 | 버린 이유 |
|---|---|---|
| Vercel 리라이트로 프록시 | 브라우저는 Vercel 의 `/api/*` 를 부르고 Vercel 이 서버에서 ALB(HTTP)로 넘긴다 | Vercel 에서 ALB 까지가 평문이다. stateless JWT 가 쿠키로 오가는데 평문 구간을 둘 수 없다 (`INF-17`) |
| `*.vercel.app` 에서 백엔드를 직접 부른다 | 프론트와 API 가 다른 사이트다 | **로그인이 안 된다.** 아래를 보라 |
| **도메인을 사서 API 와 프론트를 한 도메인 아래 둔다** | `api.lunchcatch.com` 과 `lunchcatch.com`, `owner.`, `admin.` | 채택 |

### 2.1 결정적인 이유: 인증 쿠키가 SameSite=Strict 다

lc-backend 의 `AuthCookieFactory` 는 Access 와 Refresh 를 **`HttpOnly`, `SameSite=Strict`, Domain 속성 없음**으로 내려 준다. Domain 이 없으니 쿠키는 `api.lunchcatch.com` 에만 붙는다.

브라우저는 **같은 사이트(등록 도메인이 같음)** 에서 시작한 요청에만 Strict 쿠키를 싣는다.

| 프론트가 있는 곳 | API 와의 관계 | Strict 쿠키 |
|---|---|---|
| `lunchcatch.com`, `owner.lunchcatch.com`, `admin.lunchcatch.com` | 같은 사이트 (`lunchcatch.com`) | 실린다 |
| `lunchcatch-user.vercel.app` | 다른 사이트 | **실리지 않는다.** 로그인해도 다음 요청부터 인증이 없다 |

`*.vercel.app` 으로 버티려면 쿠키를 `SameSite=None` 으로 바꿔야 하고, 그것은 CSRF 방어를 하나 걷어내는 일이며 서드파티 쿠키 차단에도 걸린다. 도메인을 사면 백엔드 쿠키 정책을 그대로 둔 채 동작한다.

**쿠키에 Domain 속성을 더할 필요가 없다.** 쿠키는 API 호스트에만 있으면 되고, 프론트 호스트는 그 쿠키를 읽지 않는다(`HttpOnly`). 같은 사이트이기만 하면 된다.

### 2.2 조직 멤버 계정에서 산 것

이 계정(762794225116)은 AWS Organizations 의 멤버다. 도메인 등록비는 통합 결제로 **조직 관리 계정**에 청구된다. 도메인 자체는 이 계정 소유라 조직을 나가도 남는다. 등록비는 AWS 크레딧으로 결제되지 않을 수 있다(기술 스택 문서의 비용 절).

## 3. 호스팅 영역은 bootstrap 에 둔다

Route 53 이 도메인을 등록하면서 호스팅 영역을 자동으로 하나 만들었다. 그것을 `bootstrap/dns.tf` 에 import 했다.

```bash
cd bootstrap && terraform import 'aws_route53_zone.main[0]' Z03486202JHZN5I319GON
```

**`terraform/` 에 두면 안 되는 이유는 네임서버다.** 영역을 지웠다 다시 만들면 네임서버 넷이 새로 배정되는데, 도메인 등록 정보의 네임서버는 따라 바뀌지 않는다. `destroy.sh` 를 돌릴 때마다 도메인이 응답하지 않게 되고 등록 정보를 손으로 고쳐야 한다. 영역 유지 비용은 월 0.5 USD 라 지켜서 잃을 것이 없다.

| 계층 | 갖는 것 | destroy 때 |
|---|---|---|
| `bootstrap/` | 호스팅 영역 (`zone_name`) | 남는다 |
| `terraform/` | ACM 인증서와 검증 레코드, HTTPS 리스너, `api` 별칭, 외부 헬스체크와 알람 둘 | 지워지고 재구축 때 다시 생긴다 |
| `bootstrap/` (4.3절) | 프론트 서브도메인이 Vercel 을 가리키는 레코드 | 남는다. 백엔드를 내려도 프론트는 떠 있다 |

`terraform/` 은 영역을 `data "aws_route53_zone"` 으로 이름으로 찾는다. 만들지 않는다.

### 3.1 도메인이 붙으면서 고친 것

**배포 스모크가 HTTPS 도메인을 찌른다.** 도메인이 있으면 ALB 의 80 은 443 으로 301 리다이렉트를 준다. `curl -f` 는 301 을 성공으로 봐서, ALB 주소로 계속 찌르면 앱이 죽어 있어도 스모크가 통과한다. `deploy.sh` 7단계가 ACM 인증서에서 도메인을 찾아 `https://api.lunchcatch.com` 을 찌른다.

**CloudWatch 알람이 7개가 된다.** 인증서 만료와 외부 헬스체크가 더해진다. 상한을 7로 올려 두었다 (`INF-42`).

**배포 역할에 `route53:ListHealthChecks` 를 더했다.** 사전 점검 PRE-1-06 이 헬스체크를 찾지 못해 "헬스체크 미설정" 으로 건너뛰고 있었다. 외부에서 서비스가 안 닿아도 배포가 진행되는 구멍이었다.

**재구축 때 `endpoint-health` 가 한 번 울린다.** 인프라를 만드는 동안 앱이 아직 없어 외부 헬스체크가 실패하고, 앱이 뜨면 OK 로 돌아온다. 2026-10-07 재구축에서 21분 동안 ALARM 이었다. 장애가 아니다.

## 4. Vercel 구성

### 4.1 누가 무엇을 갖나

**Vercel 은 프론트가 갖고, DNS 는 인프라가 갖는다.** Vercel 프로젝트는 Terraform 으로 관리하지 않는다 (`INF-44`).

| 일 | 담당 | 어디 |
|---|---|---|
| Vercel 팀, 플랜, 팀원 | 프론트 | Vercel 대시보드 |
| GitHub 앱 연결 (`lunch-catch/lc-frontend`) | 프론트. 조직 Owner 승인 | Vercel, GitHub |
| 프로젝트 셋, 빌드 설정, 환경변수 | 프론트 | Vercel 대시보드 |
| 리라이트, 헤더, 리다이렉트 | 프론트 | 앱마다 `vercel.json`. 이미 있다 |
| 프로젝트에 도메인 추가 | 프론트 | Vercel 대시보드 |
| Route 53 DNS 레코드 | 인프라 | `bootstrap/dns.tf` |
| 백엔드 CORS, 쿠키, 카카오 리다이렉트 | 인프라, 백엔드 | 6장 |

**Terraform 으로 Vercel 프로젝트를 관리하지 않는 이유.** 처음에는 Terraform 루트 `frontend/` 로 프로젝트와 도메인과 레코드를 함께 만들 생각이었다. 버린 이유는 셋이다.

* 빌드 설정과 환경변수는 프론트 코드가 정한다. 프론트가 대시보드에서 바꾸면 Terraform 상태와 어긋나고 다음 apply 가 되돌린다. 두 팀이 같은 설정의 주인이 된다.
* 환경이 운영 하나뿐이고 프로젝트가 셋이다. 코드로 찍어 낼 것이 적다.
* 빌드 설정은 이미 앱마다 `vercel.json` 으로 프론트 저장소에 있다. 코드로 남아야 할 부분은 이미 코드다.

그 대가로 인프라는 Vercel 토큰을 쥐지 않는다. 쥘 이유가 없다.

### 4.2 프로젝트

lc-frontend 는 pnpm 과 turbo 로 묶은 모노레포다. 앱마다 Vercel 프로젝트를 하나씩 둔다.

| 프로젝트 | 루트 디렉터리 | 운영 브랜치 | 도메인 |
|---|---|---|---|
| `lunchcatch-user` | `apps/user` | `main` | `lunchcatch.com`, `www.lunchcatch.com` (루트로 리다이렉트) |
| `lunchcatch-owner` | `apps/owner` | `main` | `owner.lunchcatch.com` |
| `lunchcatch-admin` | `apps/admin` | `main` | `admin.lunchcatch.com` |

프로젝트 이름은 프론트가 바꿔도 된다. 인프라는 도메인만 본다.

`main` 외 브랜치와 PR 은 Vercel 의 미리보기 배포로 `*.vercel.app` 주소에 뜬다. **미리보기에서는 2.1절 때문에 로그인이 안 된다.** 화면 확인용이다.

### 4.3 DNS 레코드

프론트가 프로젝트에 도메인을 추가하면 Vercel 이 도메인마다 넣어야 할 레코드를 보여 준다. 인프라는 그 값을 받아 `bootstrap/dns.tf` 에 넣는다.

| 도메인 | 레코드 | 대상 프로젝트 |
|---|---|---|
| `lunchcatch.com` | A | user |
| `www.lunchcatch.com`, `dev.lunchcatch.com` | CNAME | user (운영, develop) |
| `owner.lunchcatch.com`, `owner.dev.lunchcatch.com` | CNAME | owner |
| `admin.lunchcatch.com`, `admin.dev.lunchcatch.com` | CNAME | admin |
| `_vercel.lunchcatch.com` | TXT, 값 다섯 | Vercel 소유 확인 |

같은 프로젝트의 운영과 개발 주소는 같은 대상을 가리키고, Vercel 이 이름으로 브랜치를 가른다.

**소유 확인 TXT 는 이름이 하나다.** Vercel 은 도메인이 달라도 `_vercel.<영역>` 한 이름에 값을 여럿 둔다. 도메인마다 레코드를 따로 만들면 서로 덮어써 마지막 하나만 남는다.

실제 값은 `bootstrap/dns.tf` 에 있다. 문서에 박지 않는다. Vercel 이 프로젝트마다 다른 값을 주고, 프로젝트를 다시 만들면 바뀐다.

**`bootstrap/` 에 두는 이유.** 호스팅 영역과 같은 계층이라 백엔드를 `destroy.sh` 로 내려도 프론트 주소는 살아 있다. `terraform/` 에 두면 백엔드와 함께 프론트도 접속이 끊긴다.

**루트 도메인은 CNAME 이 안 된다.** DNS 규칙상 영역의 꼭대기에는 CNAME 을 둘 수 없어 A 레코드다.

### 4.4 처음 연결할 때 걸린 것 (2026-10-07, 08)

DNS 는 처음부터 맞았는데 주소가 열리지 않은 경우가 셋이었다. 모두 Vercel 설정이다. 프로젝트를 다시 만들 때 같은 순서로 확인한다.

| 증상 | 원인 | 조치 |
|---|---|---|
| 개발 주소가 Vercel 로그인 화면으로 간다 (302 -> `vercel.com/sso-api`) | Deployment Protection 이 운영이 아닌 배포를 Vercel 계정 소유자에게만 보여 준다. develop 브랜치 도메인도 걸린다 | 프로젝트마다 `Settings -> Deployment Protection -> Vercel Authentication` 을 끈다 |
| `DEPLOYMENT_NOT_FOUND`, 인증서도 없다 | 도메인이 배포본이 없는 다른 프로젝트(처음 잘못 만든 `lc-frontend`)에 붙어 있었다 | 그 프로젝트에서 도메인을 빼고 맞는 프로젝트에 다시 붙인다. 이때 Vercel 이 소유 확인 TXT 값을 새로 주므로 `bootstrap/dns.tf` 를 고친다 |
| 도메인 화면에 "No Deployment" | 프로젝트를 새로 연결한 뒤 그 브랜치의 배포가 하나도 없다. Ignored Build Step(`turbo-ignore`)이 그 앱과 무관한 커밋의 빌드를 건너뛰어 push 로는 생기지 않는다 | `Deployments -> Create Deployment` 로 `main` 과 `develop` 을 한 번씩 직접 배포한다 |

**Vercel 의 도메인 화면이 "properly configured" 라고 하면 DNS 는 끝난 것이다.** 그 뒤의 문제는 Vercel 쪽이다.

## 6. 프론트와 백엔드를 이을 때

인프라 쪽 셋은 넣었다 (2026-10-08). 운영은 다음 재구축부터, 개발은 서버를 교체할 때부터 실린다. 프론트와 카카오 콘솔 쪽이 남았다.

| 무엇 | 운영 | 개발 | 어디 | 상태 |
|---|---|---|---|---|
| CORS 허용 출처 `CORS_ALLOWED_ORIGINS` | `lunchcatch.com`, `www.`, `owner.`, `admin.` (https) | `dev.`, `owner.dev.`, `admin.dev.` (https) | `terraform/variables.tf` `frontend_origins`, `dev/variables.tf` | 완료 |
| 쿠키 Secure `JWT_COOKIE_SECURE` | 도메인이 있으면 `true`, 없으면 `false` | `true` | compose 템플릿 | 완료 |
| 카카오 리다이렉트 `KAKAO_REDIRECT_URI` | `https://lunchcatch.com/oauth/callback` | `https://dev.lunchcatch.com/oauth/callback` | `terraform/variables.tf` `kakao_redirect_uri`, 개발은 compose | 완료 |
| 카카오 콘솔의 Redirect URI 등록 | 위 운영 값 | 위 개발 값 | 카카오 개발자 콘솔 | **남음.** 없으면 카카오가 KOE006 으로 거절한다 |
| 프론트의 API 주소 | `https://api.lunchcatch.com` | `https://api.dev.lunchcatch.com` | Vercel 환경변수 (프론트) | **남음** |
| 프론트의 요청 옵션 | `credentials: 'include'` | 같음 | lc-frontend | **남음** |

**`JWT_COOKIE_SECURE` 를 도메인에 묶은 이유.** Secure 쿠키는 HTTPS 에서만 저장된다. 도메인 없이 ALB 주소(HTTP)로 올렸을 때 `true` 면 로그인해도 쿠키가 남지 않는다.

**카카오 리다이렉트는 사용자 앱 주소다.** 카카오가 인가 코드를 프론트의 `/oauth/callback`(`KakaoCallbackPage`)으로 돌려주고, 프론트가 그 코드를 API 에 넘긴다. 점주와 관리자는 카카오 로그인을 쓰지 않는다.

**개발 서버는 user-data 변경을 무시한다** (개발 서버 문서 7장). 지금 떠 있는 개발 서버의 compose 에는 카카오 리다이렉트가 없다. 다음에 `terraform -chdir=dev apply -replace=aws_instance.dev` 로 교체할 때 실린다. 교체하면 개발 DB 와 인증서가 새로 만들어진다.

## 7. 바꾸면 안 되는 것

* **호스팅 영역을 `terraform/` 으로 되돌리지 않는다.** 3장. 지우면 네임서버가 바뀐다.
* **프론트를 `*.vercel.app` 으로 운영하지 않는다.** 2.1절. 로그인이 안 된다.
* **백엔드 쿠키를 `SameSite=None` 으로 바꿔 문제를 풀지 않는다.** 같은 사이트에 두면 필요 없다.
* **같은 설정을 두 곳에서 관리하지 않는다.** Vercel 프로젝트 설정은 프론트가, DNS 레코드는 인프라가 갖는다. 4.1절.
