# 경보 대응

경보마다 무엇이 어긋났는지, 사용자가 무엇을 겪는지, 먼저 어느 화면을 보는지, 무엇을 하는지를 적는다. 경보의 `runbook_url` 이 이 문서의 절을 가리키고, critical 과 warning 의 Slack 알림에 그 링크가 붙는다. Watchdog 알림은 파이프라인이 살아 있다는 신호라 링크를 붙이지 않는다.

- 경보의 조건과 값은 `observability/prometheus/rules.yml` 이 갖는다. 이 문서는 조건을 되풀이하지 않는다
- 왜 그 경보를 두는지는 [알람과 알림 설계](../system-design/백엔드공통_알람과알림_설계.md) 5절이 갖는다
- 대시보드는 Grafana 의 폴더 이름(`2. 서비스` 등)과 대시보드 제목으로 적는다
- 경보를 더하면 이 문서에 같은 이름의 절을 더하고, 경보에 `runbook_url` 을 단다. 절 이름은 경보 이름과 같아야 링크가 맞는다

## Watchdog

- **뜻:** 알림 파이프라인이 살아 있다는 신호다. 항상 울리고 5분마다 다시 온다
- **영향:** 없다
- **대응:** 이 알림이 끊기면 Prometheus, Alertmanager, Slack 웹훅 가운데 하나가 죽은 것이다. 모니터링 서버의 컨테이너 상태부터 본다

## CacheOomRejected

- **뜻:** Valkey 가 메모리가 다 차 쓰기를 거절했다. 퇴출 정책이 noeviction 이라 오래된 키를 지우지 않는다
- **영향:** 로그인 상태, 쿠폰 순번, 과금 쓰기가 실패한다
- **먼저 볼 곳:** `5. 의존 시스템` > `2. 인메모리 DB` 의 메모리 사용량과 메모리가 차서 거절한 쓰기
- **대응:** TTL 없는 키와 키 개수를 확인해 정리한다. 정리로 모자라면 노드를 키운다

## HighFiveXXRate

- **뜻:** 5xx 비율이 1시간 전의 2배를 넘었다. 배포가 원인인지 가르는 경보다
- **영향:** 사용자 요청이 실패한다
- **먼저 볼 곳:** `1. 개요` > `시스템 개요` 의 5xx 비율과 배포 주석, `2. 서비스` > `2. API` 의 API별 5xx 비율
- **대응:** 직전에 배포가 있었으면 롤백을 판단한다. 배포가 없으면 5xx 가 몰린 API 에서 트레이스와 오류 로그를 본다

## BatchAllDown

- **뜻:** 살아 있는 배치 서버가 없다
- **영향:** 00:00 묶음, 쿠폰 만료 같은 영업일 경계 작업이 돌지 않는다
- **먼저 볼 곳:** AWS 콘솔의 배치 ASG 활동 이력
- **대응:** ASG 가 인스턴스를 교체하는지 확인한다. 경계 시각을 넘겼으면 그날 작업을 손으로 다시 돌릴지 판단한다

## MysqlConnectionFailed

- **뜻:** mysqld_exporter 가 MySQL 에 닿지 못한다
- **영향:** 캐시와 달리 강등할 경로가 없어 거의 모든 요청이 실패한다
- **먼저 볼 곳:** AWS 콘솔의 RDS 상태와 이벤트(페일오버), `5. 의존 시스템` > `1. RDB`
- **대응:** RDS 가 살아 있으면 보안 그룹과 exporter 컨테이너를 본다. 페일오버 중이면 끝난 뒤 앱이 다시 붙는지 확인한다

## CpuSurplusCreditInUse

- **뜻:** EC2 가 크레딧을 다 쓰고 초과분을 한 시간 넘게 빌려 쓰고 있다
- **영향:** 느려지지는 않는다. 24시간 안에 갚지 못하면 과금된다
- **먼저 볼 곳:** `6. 인프라` > `1. 호스트` 의 CPU 크레딧 줄과 CPU 사용률
- **대응:** 기준선보다 오래 바쁜 원인(부하, 멈추지 않은 작업)을 찾는다

## CpuSurplusCreditCharged

- **뜻:** 빌려 쓴 초과분 크레딧이 실제로 과금됐다
- **영향:** 비용이 나간다
- **먼저 볼 곳:** `6. 인프라` > `1. 호스트` 의 EC2 CPU 잉여 크레딧
- **대응:** 부하 원인을 확인한다. 상시 바쁘면 인스턴스 크기를 다시 본다

## HikariPendingHigh

- **뜻:** DB 커넥션 풀에서 커넥션을 기다리는 스레드가 9 를 넘었다
- **영향:** 대기가 쌓이면 톰캣 스레드가 먼저 말라 요청이 느려진다
- **먼저 볼 곳:** `4. 런타임` > `애플리케이션 서버 자원` 의 DB 커넥션 풀 줄, `5. 의존 시스템` > `1. RDB` 의 Slow query
- **대응:** 느린 쿼리와 커넥션을 오래 쥔 코드를 찾는다

## HikariConnectionTimeout

- **뜻:** 풀에서 커넥션을 시간 제한 안에 얻지 못해 요청이 실패했다
- **영향:** 그 요청이 실패한다
- **먼저 볼 곳:** `4. 런타임` > `애플리케이션 서버 자원` 의 DB 커넥션 풀 줄
- **대응:** 풀 크기와 오래 쥔 커넥션을 확인한다

## TransactionSlow

- **뜻:** 커넥션을 1초 넘게 쥔 사용이 1% 를 넘었다
- **영향:** 커넥션이 묶여 다른 요청이 기다린다
- **먼저 볼 곳:** `4. 런타임` > `애플리케이션 서버 자원` 의 트랜잭션 시간
- **대응:** 누수 감지 경고 로그로 커넥션을 오래 쥔 코드를 찾는다

## GcOverheadHigh

- **뜻:** 시간의 10% 넘게 GC 로 멈췄다. 메모리가 모자라기 시작한 가장 이른 신호다
- **영향:** 요청이 그만큼 멈춘다
- **먼저 볼 곳:** `4. 런타임` > `애플리케이션 서버 자원` 의 GC 로 멈춘 시간 비율과 GC 뒤에 남은 힙
- **대응:** GC 뒤에 남은 힙이 함께 오르는지 본다. 오르면 HeapAfterGcHigh 의 대응을 따른다

## HeapAfterGcHigh

- **뜻:** GC 를 해도 힙의 70% 넘게 비워지지 않는다
- **영향:** 그대로 가면 OutOfMemoryError 로 죽는다
- **먼저 볼 곳:** `4. 런타임` > `애플리케이션 서버 자원` 의 GC 뒤에 남은 힙
- **대응:** 시간이 갈수록 오르면 메모리 누수다. 평평하게 높으면 힙 크기를 다시 본다

## CacheConnectionFailed

- **뜻:** redis_exporter 가 Valkey 에 1분 넘게 닿지 못한다
- **영향:** 캐시는 죽어도 서비스가 돌도록 강등 경로를 둔다. 광고 서빙은 일부 규칙을 건너뛴다
- **먼저 볼 곳:** `5. 의존 시스템` > `2. 인메모리 DB`, `3. 도메인` > `1. 광고 서빙` 의 캐시 장애로 건너뛴 규칙
- **대응:** 강등 경로가 실제로 도는지 확인하고 ElastiCache 상태를 본다

## CacheMemoryHigh

- **뜻:** Valkey 메모리가 상한의 70% 를 넘었다
- **영향:** 아직 없다. 다 차면 CacheOomRejected 가 된다
- **먼저 볼 곳:** `5. 의존 시스템` > `2. 인메모리 DB` 의 메모리 사용량
- **대응:** TTL 없는 키와 키 개수를 확인한다

## ContainerRestartLoop

- **뜻:** 컨테이너가 10분 안에 3번 이상 다시 떴다
- **영향:** 그 컨테이너가 맡은 일이 끊긴다
- **먼저 볼 곳:** `6. 인프라` > `1. 호스트` 의 컨테이너 재기동과 컨테이너 메모리
- **대응:** OOM 이 가장 흔한 원인이다. 컨테이너 로그와 메모리 상한을 본다

## NodeMemoryHigh

- **뜻:** 기계의 메모리 사용률이 15분 넘게 90% 를 넘었다
- **영향:** 더 차면 커널이 프로세스를 죽인다
- **먼저 볼 곳:** `6. 인프라` > `1. 호스트` 의 메모리 사용률과 컨테이너 메모리
- **대응:** 어느 컨테이너가 메모리를 쓰는지 보고 OOM 로그를 확인한다

## RdsStorageLow

- **뜻:** RDS 의 남은 저장 공간이 2GiB 아래다. 저장 공간 자동 확장을 켜지 않았다
- **영향:** 다 차면 쓰기가 멈춘다
- **먼저 볼 곳:** `5. 의존 시스템` > `1. RDB` 의 남은 저장 공간
- **대응:** 오래된 데이터를 정리하거나 `modules/data/rds.tf` 의 `allocated_storage` 를 올린다. 올리면 경보의 값도 함께 고친다

## RdsFreeableMemoryLow

- **뜻:** RDS 의 여유 메모리가 15분 넘게 256MiB 아래다
- **영향:** 연결이 몰리거나 버퍼 풀이 메모리를 밀어내 쿼리가 느려진다
- **먼저 볼 곳:** `5. 의존 시스템` > `1. RDB` 의 여유 메모리, MySQL 연결 수, Slow query
- **대응:** 연결 수와 느린 쿼리를 확인한다. 인스턴스 클래스를 바꾸면 경보의 값도 함께 고친다

## MysqlConnectionsHigh

- **뜻:** MySQL 연결이 `max_connections` 의 90% 를 넘었다
- **영향:** 다 차면 새 연결이 거절돼 커넥션 풀이 마른다
- **먼저 볼 곳:** `5. 의존 시스템` > `1. RDB` 의 MySQL 연결 수
- **대응:** 커넥션 풀 크기와 오래 쥔 연결을 확인한다

## DiskUsageHigh

- **뜻:** 디스크 사용률이 80% 를 넘었다
- **영향:** 다 차면 로그와 데이터를 쓰지 못한다
- **먼저 볼 곳:** `6. 인프라` > `1. 호스트` 의 디스크 사용률
- **대응:** 로그를 정리한다

## BatchDegraded

- **뜻:** 배치 서버 두 대 가운데 한 대만 살아 있다
- **영향:** 남은 한 대가 작업을 이어받아 지금은 돈다. 그것마저 죽으면 BatchAllDown 이 된다
- **먼저 볼 곳:** `1. 개요` > `시스템 개요` 의 배치 서버 수, AWS 콘솔의 배치 ASG
- **대응:** 죽은 쪽을 확인한다

## BatchNotRun

- **뜻:** 배치 작업이 주기를 넘겨 성공하지 못했다. 서버마다 따로 본다
- **영향:** 작업마다 다르다. 00:00 묶음이면 그날 캠페인과 정산이 틀어진다
- **먼저 볼 곳:** `2. 서비스` > `3. 백그라운드 작업` 의 마지막 성공 이후 경과(기준 대비)
- **대응:** 그 서버의 스케줄러가 멈췄는지 배치 로그로 본다

## ApiLatencyHigh

- **뜻:** API 의 p99 가 10분 넘게 그 API 의 목표를 넘었다
- **영향:** 사용자가 느린 응답을 겪는다
- **먼저 볼 곳:** `2. 서비스` > `2. API` 의 기준을 넘은 API
- **대응:** 넘은 점을 눌러 트레이스를 열고 오래 걸린 단계를 찾는다. 위쪽 링크의 프로파일로 코드 위치를 좁힌다

## TargetDown

- **뜻:** 수집 대상이 5분 넘게 응답하지 않는다
- **영향:** 그 대상의 지표를 보는 경보가 울리지 않은 채 멈춘다
- **먼저 볼 곳:** `6. 인프라` > `2. 모니터링 상태` 의 모니터링 구성 요소가 살아 있는지
- **대응:** 그 대상의 컨테이너를 확인하고 다시 띄운다

## PrometheusRuleEvaluationFailures

- **뜻:** Prometheus 가 규칙 묶음 안의 규칙을 평가하다 오류가 났다. 한 번만 실패해도 울린다
- **영향:** 실패한 규칙의 경보가 그동안 평가되지 않았을 수 있다. 같은 묶음의 다른 규칙이 멈췄다는 뜻은 아니다
- **먼저 볼 곳:** `6. 인프라` > `2. 모니터링 상태` 의 규칙 평가 실패, Prometheus 로그
- **대응:** Prometheus 로그에서 실패한 규칙을 찾아 고친다. 바꾼 규칙은 `promtool check rules` 와 `promtool test rules` 로 확인한다

## TraceDroppedBeforeDecision

- **뜻:** 앱 서버의 Alloy 가 테일 샘플링 판정을 기다리던 트레이스를 판정 전에 버렸다. 판정 버퍼(`num_traces`, 기본 50,000)가 차면 가장 오래된 것부터 버린다
- **영향:** 버린 트레이스는 오류나 느린 요청이어도 남지 않는다. 앱 지표와 로그는 그대로다
- **먼저 볼 곳:** `6. 인프라` > `2. 모니터링 상태` 의 판정 전에 버린 트레이스, `2. 서비스` > `2. API` 의 그 서버의 요청 수
- **대응:** 트래픽이 잠깐 몰린 것이면 지나가길 본다. 이어지면 `observability/alloy/tracing.alloy` 의 `num_traces` 를 늘리거나 `decision_wait` 를 줄인다. `num_traces` 를 늘리면 Alloy 의 메모리를 더 쓰니 TraceSpansRefused 도 함께 본다. `decision_wait` 를 줄이면 그보다 늦게 오는 스팬(오래 걸리는 백그라운드 작업의 루트 등)이 판정에 들지 않아, 늦게 온 오류나 느린 스팬이 있는 트레이스가 빠지거나 일부만 남는다. 그래서 `num_traces` 를 먼저 늘린다

## TraceSpansRefused

- **뜻:** 앱 서버의 Alloy 가 메모리 한도(`memory_limiter`)에 닿아 스팬을 거절했다
- **영향:** 거절된 스팬은 앱의 에이전트가 다시 보내고, 다시 보내기도 실패하면 그 트레이스가 빠진다. 앱 서버의 메모리는 지켜진다
- **먼저 볼 곳:** `6. 인프라` > `2. 모니터링 상태` 의 Alloy 가 거절한 스팬과 Tempo 가 거절한 스팬, `4. 런타임` > `애플리케이션 서버 자원` 의 컨테이너 메모리
- **대응:** Tempo 도 거절하고 있으면 TempoSpansDiscarded 부터 푼다. Alloy 가 다시 보내려고 쌓은 것이 메모리를 채운 것이다. Tempo 가 멀쩡하면 트래픽이 몰린 것이다. 이어지면 Alloy 의 컨테이너 메모리 한도를 늘린다

## TempoSpansDiscarded

- **뜻:** Tempo 가 기본 한도에 닿아 스팬을 거절했다. 까닭은 경보의 `reason` 이다. 초당 30MB 를 넘으면 `rate_limited`, 살아 있는 트레이스가 10,000 을 넘으면 살아 있는 트레이스 초과로 나온다
- **영향:** 앱 서버의 Alloy 가 다시 보내려고 쌓아 메모리가 는다. 다시 보내기도 실패하면 그 트레이스가 빠진다
- **먼저 볼 곳:** `6. 인프라` > `2. 모니터링 상태` 의 Tempo 가 거절한 스팬, `6. 인프라` > `1. 호스트` 의 모니터링 서버 메모리
- **대응:** 장애로 느린 요청과 오류가 한꺼번에 늘면 모두 남기는 정책 때문에 양이 는다. 장애가 끝나면 그친다. 평소에도 이어지면 `observability/tempo/config.yaml` 의 `overrides` 에서 한도를 올리거나 Alloy 에 전체 양의 상한을 둔다

## CacheEngineCpuHigh
